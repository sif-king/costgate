## 0. 结论先行

1. **后端与代理转发层是健康的，前端面板是塌的。** 2026-10-23 全真跑测试基线为 manager 1615 pass / 0 fail（`docs/01-feature-matrix.md:85`），但同一时间真实浏览器取证显示 **11/11 页面 `themeLinked=false`**（audit.json:207、321、391、457、521、677、793、913、959、1165、1203），`settings` / `legal` 两页导航项数为 0、进去出不来（audit.json:920、1172）。测试绿与可用之间隔着一整个前端。
2. **本轮立项的对象是「面板可观测与可用性重构」，不是代理内核重写。** 三笔工程账（用量归一 `lib/usage-probe.js:21-30`、base_url 单一所有者 `lib/agent-owner.js`、本地模型是一档路由条件 `README.md:345`）全部不动。
3. **验收只认真实浏览器。** jest 全绿不构成任何一条验收标准（理由见 §4.1，取证报告 §0 已有方法论纠错）。
4. **v1.0 范围收敛为 6 件事**：统一品牌、统一导航、统一 CSS 体系并接入明暗主题、修复 proxy-config 数据口径、清理占位/空页、建立真实浏览器 E2E 验收设施。开放项 A–F 拍板后即冻结范围。

## 1. 背景与问题陈述

### 1.1 项目是什么（一句话）

multi-proxy 是本地优先的 AI Agent 编排中枢：本机起 9 个 OpenAI 兼容代理（codex 18790 / claude 18791 / manager 18792 / hermes 18793 / cursor 18794 / dsh 18797 / opencode 18798 / generic 18799 / opencode-free 18800），把多个 coding agent 当「员工」统一管配置、用量、冲突与健康（`README.md:7-13`、`README.md:87-101` 端口表）。管理面板入口为 `multi-proxy-manager/server.js`（页面路由 `server.js:205-222`，端口读环境变量 `PORT`）。

### 1.2 老板的批评（本项目的直接起因）

- **UI 现状极差**：真实浏览器取证下 11/11 页存在导航断裂、主题不联动、数据口径互相矛盾等 P0 缺陷（取证报告 §3，共 9 条 P0）。
- **不能拿 jest 绿当验收**：上一轮以「jest 1615/1615 全绿」宣称开箱即用，结论不成立——前端测试只断言字符串存在，测不出图标压字、栅格错位、主题不联动（取证报告 §0 表格，`docs/09-review/UI现状取证报告-2026-10-23.md:12-22`）。仓内有 6 个 E2E spec / 720 行 / 50 用例，但 `package.json` 无 e2e script、浏览器未下载，从未真实跑过（取证报告 `:17-18`）。

### 1.4 为什么必须文档先行

取证的教训是「实现跑在验收前面、验收跑在需求前面」：`proxy-config.html` 漏改 3→9 代理（P-6）正是因为没有一份功能清单约定「所有列代理的页面必须同源同数」。本轮先冻结需求与正负例（本系列文档），再实施，再按 §4 指标真实浏览器验收。

## 2. 目标用户与核心场景

| 用户 | 画像 | 核心场景 | 对面板的诉求 |
|------|------|----------|--------------|
| U1 本机开发者（自己） | 在一台 Mac 上同时跑 codex / claude / opencode / hermes / cursor 等多个 agent，深度参与本项目开发 | ① 早上开面板看 9 个代理是否全绿；② 发现某个 agent 流量异常，进 proxy-config 查当前模型与路由；③ 出错时进日志页按代理+级别过滤定位 | 首屏 30 秒内看到全部 9 个代理真实状态；日志过滤一步到位；页面间跳转不迷路 |
| U2 想省钱的个人用户 | 用 Cline / Aider / OpenHands + Claude Code，接了几家 API 供应商，关心 token 花在哪 | ① 看 floor / context 页了解用量与上下文构成；② 对账 cost-ledger；③ 决定哪些任务派给本地 Ollama（privacy 路由） | 成本/用量数字口径一致、能看懂；明暗主题跟随 OS（夜间写代码） |
| U3 多 agent 并存的重度用户 | 本机还有 cc-switch 等工具，历史上出现过 base_url 双所有者事故（`README.md:165`） | ① 开代理前确认所有权冲突检测状态；② 影子模式观察路由建议不动真实流量；③ 设置页撤销首启同意、导出配置备份 | 冲突状态在 dashboard 一眼可见；settings 可达且有真实功能；界面不出现「示例/占位」这类不专业文本 |

共同点：三者都在**本机**使用（面板绑定 127.0.0.1，`README.md:311`），单用户，无多租户需求——这决定了 UI 可以做重「信息密度」而不必做「引导式 onboarding」。

## 4. 成功指标（全部可在真实浏览器判定）

### 4.1 验收方法论（先立规矩）

- **唯一验收手段是真实浏览器 E2E**：复用取证报告的方法——隔离实例（`HOME=/tmp/... PORT=18801 MP_CONSENT_BYPASS=1 node server.js`，取证报告 :29）+ playwright/puppeteer 实渲染 + 截图留档 + computed style 断言。
- **jest 绿不构成任何一条验收**。理由：前端测试只断言字符串存在，测不出栅格、主题、图标（取证报告 :16）；本轮 E2E 设施落地前，任何「已完成」的说法均无效。
- 每条指标定义「取证同款度量」的判定方式，验收时重新跑 audit 脚本，产出与 `docs/09-review/ui-audit-2026-10-23/audit.json` 同构的报告作对照。

### 4.2 量化指标

| M# | 指标 | 基线（2026-10-23） | v1.0 目标 | 判定方式（真实浏览器） |
|----|------|--------------------|-----------|------------------------|
| M1 | `themeLinked=true` 页面数 | 0/11（audit.json 各页） | **13/13**（含 login / consent 补测） | `emulateMediaFeatures(prefers-color-scheme)` 切换后 `body` computed style 两态不同 |
| M2 | 导航项数收敛 | 0~24 五套并存 | 每页 ≤10 且全站同一套链接集合；settings/legal ≥1 条返回路径 | audit 脚本 navLinks 断言 |
| M3 | CSS 加载数 | 0/2/4 三种 | 全站统一为 1 套（≤4 个且每页相同集合） | audit.json sheets 逐页比对 |

## 5. 范围拆解

### 5.1 v1.0 范围（本立项）

按页面 × 主题两条线执行，功能点级拆解见《`docs/design/03-功能清单与正负例.md`》（≥40 条，每条带正负例）：

1. **设计 token 收口**：以 `tokens.css` 为唯一 token 源（`tokens.css:93` 已含暗色变量），废弃/合并 `colors_and_type.css` 的旧色板；全部页面统一加载同一组 CSS。
2. **导航组件化**：单一 nav 组件（进化自 `public/nav.js`）铺到 13 页；settings/legal 至少有「返回」路径（进主导航与否见开放项 C）。
3. **主题联动服务**：一个 theme.js——读 `prefers-color-scheme` + localStorage 覆盖 → 写 `html[data-theme]`；settings 页开关接真实现（现在 `settings.html:136-139` 的 toggle 只切无效的 body class）。
4. **数据同源修复**：proxy-config 从与 dashboard 相同的 9 代理 API 渲染。
5. **布局与图标**：统一 12 栅格卡片布局；图标收敛为一套（具体方案开放项 E）。
6. **文案清理**：清掉 P-10 的占位文本；settings「更新」卡片改为真实状态（有更新源则接，没有则显示「本地版本 vX」而非占位话术）。
7. **E2E 验收设施**：playwright 安装 + `npm run e2e` + 按 03 文档正负例逐条落地 + 每次验收产出 audit.json 同构报告。

### 5.2 后续（v1.1+，不承诺时间）

- 桌面壳 splash / Dock / 主题跟随验证（需真机 GUI）。
- legal 页内容结构化渲染（条款目录、锚点导航）。
- floor / context 页在明暗两态下的图表配色精修。
- 移动端适配（若出现真实需求）。
- 安装脚本补齐 claude / opencode / generic 的 install 函数（README `:256` 已声明的代码层缺口，与 UI 无关但记录在案）。

## 7. 待老板拍板的开放项

> 每条含选项 / 代价 / 建议。拍板后范围即冻结。

### (A) 品牌名统一为哪个？

- **选项 1：`Multi-Proxy`（产品名）**，面板侧栏显示 `Multi-Proxy Manager`。
  - 代价：改 `logs.html:6,659`、`skills.html:6,108`、`sessions.html:6,86`、`knowledge.html:6,90`、`dashboard.html`（title 与侧栏）、`floor.html:6,52`、`context.html:6,65`、`settings.html:6,56` 约 8 个文件的 title/侧栏；`consent.html:6,54` 已是此写法不用改。
- **选项 2：`Proxy Manager`**。
  - 代价：与仓库名 / README 口径（`README.md:7`「Multi-Proxy」）冲突，且 settings/consent/floor/context 都要反向改，改动面更大；对外叙事也要跟着改。
- **选项 3：其他新名**。
  - 代价：全部 13 页 + README + llms.txt + desktop 壳全部改，另需同步对外文档，成本最高。
- **建议：选项 1**。理由：README 对外定位已用 Multi-Proxy（`README.md:7-11`），settings/consent 两页已是 `Multi-Proxy Manager`，改存量 8 个文件的字符串即可全站唯一，且不牵动对外叙事。

### (B) 暗色模式是否必须支持「跟随 OS」？

- **选项 1：跟随 OS（`prefers-color-scheme`）+ 手动切换（三态：跟随/亮/暗，localStorage 记忆）**。
  - 代价：一个 theme.js 联动服务 + settings 三态开关；`tokens.css:93` 暗色变量已存在，主要是补联动与覆盖度验证（R3）。
- **选项 2：只做手动切换**。
  - 代价：实现更少，但 settings 页现有文案「跟随本机外观或手动固定」（audit.json:936）必须改口，且与用户预期不符（夜间开发场景）。
- **建议：选项 1**。理由：文案承诺已存在（P-3），token 基础已在，边际成本低；三态设计同时满足「跟随」与「强制」两种预期，M1 指标按此定义。

### (C) settings 和 legal 是否进主导航？

- **选项 1：settings 进主导航，legal 不进**（legal 从 settings「法务」卡片与首启 consent 页链接进入，legal 保留显式「← 返回」）。
  - 代价：nav 组件加 1 项；legal 页加返回链 + CSS。
- **选项 2：两者都进主导航**。
  - 代价：legal 是 7770 字符长文页（audit.json:1183），进主导航会诱导误入；导航项数压力增大。
- **选项 3：都不进，仅保留 dashboard 现有入口按钮**。
  - 代价：settings 现状在 dashboard 导航第 8 项本就有入口（audit.json:47-51），但 legal 从任何导航都到不了的状态（P-4）必须解决，此选项治标。
- **建议：选项 1**。理由：settings 是高频功能页应直达；legal 是低频合规页，二级入口 + 返回路径即可满足，避免导航膨胀。

### (D) 现有 13 个页面在 v1.0 是否全保留？哪些合并/下线？

13 页清单：dashboard / index / floor / context / proxy-config / sessions / knowledge / skills / logs / settings / legal / login / consent。

- **建议逐页裁决如下（待拍板）**：
  | 页面 | 建议 | 理由 |
  |------|------|------|
  | index | **与 dashboard 合并后 302 到 dashboard**（v1.0 内做跳转壳，v1.1 下线文件） | audit.json 中两页 textLen 同为 1595、navLinks 完全相同（:6-208 vs :964-1166），是纯重复页 |
  | dashboard | 保留，作为唯一概览页 | 数据最全（9 代理 + 版本 + 任务 + 健康） |
  | floor / context | 保留，导航改统一组件 | 是成本/上下文观测的核心页；floor 200px 卡片按 G4 修 |
  | proxy-config | 保留，修 3→9 数据口径（P-6） | 供应商/模型/余额唯一管理入口 |
  | sessions | 保留，补空态设计（现正文仅 132 字符，audit.json:424） | 后端 23/23 jest 的任务管理能力对应此页（`docs/01-feature-matrix.md:42`），不能下线 |
  | knowledge / skills | 保留 | 门控默认关是预期（R5），修门控说明文案即可 |
  | logs / settings / legal / login / consent | 保留 | 各自职责清晰 |
- **选项 2：13 页全保留不合并**——代价是 index 的 24 项导航与 dashboard 双份维护继续存在，P-4 治不了根。
- **建议：选项 1（合并 index）**。理由：重复页是导航混乱的最大来源，合并是零功能损失的减法。

### (E) 图标体系选哪套？

- **选项 1：单一内联 SVG 图标集**（自绘或引入单个开源集，随组件走，无运行时依赖）。
  - 代价：约 20 个图标的绘制/挑选 + 组件封装。
- **选项 2：保留字符/emoji 但统一规范**（如统一用某一区段符号）。
  - 代价：最低，但跨平台渲染不一致，且与「专业工具」定位不符（P-11 现状即此路线的恶果）。
- **建议：选项 1**。理由：本地面板无 CDN 依赖约束下，内联 SVG 是唯一可控且跨态（明暗主题自动 currentColor）的方案；工作量一次性。

### (F) dashboard 的 5 个无落地 BUTTON（健康状态/告警中心/Agent 注册表/成本/影子模式）如何处置？

- **现状**：它们是 BUTTON 而非链接（audit.json:53-76 tag=BUTTON href=null），取证未验证点击行为（取证报告 :138）。
- **选项 1：实施前逐个点击取证**，有真实行为的保留并接导航，无行为的 v1.0 先隐藏。
- **选项 2：全部保留原样**，仅做样式统一。
  - 代价：可能留下 5 个死按钮，与 G5 冲突。
- **建议：选项 1**。理由：先取证再裁决，避免误删真实功能入口，也避免死按钮进 v1.0。
